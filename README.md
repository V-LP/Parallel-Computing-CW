# Паралельна пошукова система з LLM

Курсова робота з паралельних обчислень.

## Опис

Контейнеризована пошукова система на Java 21. Вона будує інвертований індекс над текстовим
датасетом паралельно (власний thread pool і власна thread-safe структура даних), обробляє
запити від кількох клієнтів одночасно та розширює запит за допомогою локальної LLM (Ollama).

Можливості:

- паралельна побудова інвертованого індексу;
- пошук за ключовими словами;
- розширення запиту (query expansion) через Ollama; якщо Ollama недоступна, пошук іде по
  оригінальному запиту;
- REST API та WebSocket `/ws/search`;
- клієнти: консольний (CLI) і веб-інтерфейс (Web UI);
- запуск однією командою `docker compose up`.

> Статус: реалізовано індексацію, пошук за ключовими словами, клієнт Ollama з розширенням запиту (етап 8) WebSocket `/ws/search` (етап 9) і консольний клієнт CLI (етап 10). Web UI додається поетапно, див. `CONTEXT.md`.

## Вимоги

- Docker та Docker Compose (для запуску системи);
- JDK 21 та Maven 3.9+ (лише для локальної розробки без Docker; CLI можна запускати і без них через `docker compose run --rm cli`);
- Python 3.10+ з `matplotlib` (лише для бенчмарків у `bench/`);
- місце під розпакований датасет (за описом завдання ~1,7 ГБ для `D1.7GB.zip`);
- пам'ять: індекс зберігається в оперативній пам'яті (див. розділ "Пам'ять").

## Запуск

Запуск усієї системи (сервер + Ollama) однією командою:

```bash
docker compose up --build
```

Сервіси:

| Сервіс | Порт | Призначення |
|--------|------|-------------|
| `server` | 8080 | пошуковий сервер (REST API) |
| `ollama` | 11434 (лише всередині мережі compose) | локальна LLM |

Змінні середовища:

| Змінна | За замовчуванням | Опис |
|--------|------------------|------|
| `PORT` | `8080` | порт сервера |
| `OLLAMA_URL` | `http://ollama:11434` | адреса Ollama |
| `OLLAMA_MODEL` | `qwen2.5:1.5b` | модель для розширення запиту |
| `OLLAMA_TIMEOUT_SECONDS` | `60` | таймаут однієї генерації в Ollama |
| `DATA_DIR` | `/data` | каталог з `.txt` файлами датасету (в Docker це `./data`) |
| `CHUNK_SIZE_KB` | `100` | розмір чанка книги в КБ (символів); `0` вимикає чанки (файл = документ) |
| `SEARCH_THREADS` | кількість CPU | розмір власного пулу потоків для WebSocket-запитів |

Каталог `./data` монтується в контейнер сервера як `/data` (лише читання).

Перевірка, що сервер працює:

```bash
curl localhost:8080/api/health
# {"status":"ok","ollama":true}
```

Якщо Ollama ще не готова, поле `ollama` буде `false`: сервер при цьому працює.

Збірка fat-jar і запуск без Docker:

```bash
mvn -pl server -am package
PORT=8080 OLLAMA_URL=http://localhost:11434 java -jar server/target/server.jar
```

Локальна збірка:

```bash
mvn compile            # компіляція всіх модулів
mvn test               # тести
mvn spotless:apply     # автоформатування (Google Java Style)
```

## API

| Метод | Шлях | Тіло запиту | Відповідь |
|-------|------|-------------|-----------|
| GET | `/api/health` | - | `{ "status": "ok", "ollama": true }` |
| POST | `/api/index` | `{ "threads": 4 }` | `{ "status": "ok", "documents_indexed": N, "time_ms": T }` |
| POST | `/api/search` | `{ "query": "text", "mode": "keyword" }` | `{ "results": [{"doc_id": "...", "score": 0.95, "snippet": "..."}], "time_ms": T }` |
| GET | `/api/stats` | - | `{ "documents": N, "index_build_time_ms": T, "threads_used": K }` |

Помилки `POST /api/index` і `POST /api/search` (тіло `{ "status": "error", "message": "..." }`):

| Код | Коли |
|-----|------|
| 400 | `/api/index`: некоректний JSON або `threads` поза межами 1..1024 (без тіла або без `threads` береться кількість процесорів). `/api/search`: порожній або відсутній `query`, `mode` не `keyword`, некоректний JSON |
| 409 | інша індексація ще триває |
| 500 | каталог даних (`DATA_DIR`) недоступний |

WebSocket `/ws/search`: див. розділ "WebSocket" нижче.

## WebSocket

`ws://localhost:8080/ws/search`. Клієнт надсилає `{"query": "..."}`, сервер надсилає окремі
повідомлення, кожне одразу, як етап готовий:

```json
{"stage":"query_expansion","data":{"original":"white whale","expanded_terms":["ship","harpoon"]}}
{"stage":"keyword_search","data":{"results":[{"doc_id":"...","score":1.0,"snippet":"..."}],"time_ms":12}}
{"stage":"done"}
```

- `time_ms` це час лише етапу пошуку (без очікування Ollama).
- Ollama недоступна, повільна або зайнята: `expanded_terms` це `[]`, пошук іде по оригіналу.
- Порожній індекс: ті самі три повідомлення з порожнім `results`.
- Помилковий вхід (не JSON, немає або порожній `query`, `query` не рядок, довше 1000 символів):
  `{"stage":"error","data":{"message":"..."}}`, потім `{"stage":"done"}`. З'єднання лишається
  відкритим, можна слати наступний запит.
- Запити одного з'єднання виконуються по черзі (у черзі до 16, зайві отримують `error` + `done`).
- Кожен запит виконується у власному пулі потоків (`SEARCH_THREADS`), а не на потоці Jetty:
  повільна Ollama не блокує інші з'єднання. Ліміт простою WebSocket піднято з 30 с до 10 хв, щоб
  з'єднання не рвалося, поки сервер чекає на модель.

**Ручна перевірка без Node.js і Maven** (достатньо JDK 21, сервер уже запущено):

```powershell
java tools/WsClient.java "white whale"
java tools/WsClient.java "white whale" --url ws://localhost:8080/ws/search --timeout 120
```

Клієнт друкує кожне повідомлення з міткою часу і часом від відправки запиту, наприклад:

```
14:03:11.220  connected
14:03:11.224  sending {"query":"white whale"}
14:03:12.870  [+1646 ms]  {"stage":"query_expansion", ...}
14:03:12.881  [+1657 ms]  {"stage":"keyword_search", ...}
14:03:12.882  [+1658 ms]  {"stage":"done"}
```

(Часи лише ілюстрація формату, не вимірювання.) Код виходу: 0 = отримано `done`, 1 = помилка
з'єднання або таймаут.

## CLI

Консольний клієнт у модулі `cli` (пакет `ua.coursework.cli`, лише JDK, без Javalin). За замовчуванням
він шукає через WebSocket `/ws/search` і друкує етапи в міру надходження.

### Запуск

Сервер має працювати (`docker compose up`). Скрипти лежать у корені репозиторію:

| ОС | Команда |
|----|---------|
| Linux, macOS, Git Bash | `./search "white whale"` |
| Windows (cmd) | `search.cmd "white whale"` |
| Windows (PowerShell) | `.\search.ps1 "white whale"` |

Скрипт запускає `cli/target/search-cli.jar`. Якщо jar ще немає, він сам збирає його
(`mvn -q -pl cli -am package -DskipTests`), а якщо немає Maven або JDK, пише зрозуміле повідомлення.
Після зміни коду CLI перезберіть jar вручну тією ж командою.

Без локальної Java, через Docker (сервіс `cli` має профіль `cli`, тому `docker compose up` його не
запускає):

```bash
docker compose run --rm cli "white whale"
docker compose run --rm cli --health
```

### Команди й параметри

```text
search "запит"              пошук через WebSocket (розширення запиту + пошук)
search white whale          лапки не обов'язкові: слова з'єднуються пробілом
search "запит" --rest       пошук через POST /api/search (mode: keyword, без розширення)
search "запит" --json       друкувати сирий JSON (WebSocket: по рядку на повідомлення)
search --health             GET /api/health
search --stats              GET /api/stats
search --index              POST /api/index (потоки = кількість CPU)
search --index 4            POST /api/index з threads = 4
search --help               довідка
search - < query.txt        запит зі stdin (UTF-8)
```

| Параметр | За замовчуванням | Опис |
|----------|------------------|------|
| `--url АДРЕСА` | `$SEARCH_URL`, інакше `http://localhost:8080` | адреса сервера (`http(s)://`, `ws(s)://` або `host:port`) |
| `--timeout СЕК` | пошук 120 с, `--health` і `--stats` 10 с, `--index` 30 хв | таймаут очікування відповіді |
| `--rest` | вимкнено | пошук через REST замість WebSocket |
| `--json` | вимкнено | сирий JSON замість форматованого тексту |

Приклад виводу (формат ілюстративний, числа не є вимірюванням):

```text
$ ./search "white whale"
Розширення: moby, dick, harpoon
1. melville/moby.txt#12  1.0000
    ...the white whale swam slowly past the ship, and the crew watched in silence while the
    captain gave his orders...
2. other/sea.txt#3  0.4120
    ...
Час пошуку: 14 мс
Готово.
```

Якщо Ollama недоступна, перший рядок такий: `Розширення: немає (Ollama недоступна)`, а пошук іде по
оригінальному запиту. Сніпети переносяться по ширині 100 символів.

```powershell
.\search.ps1 --health
# Сервер: ok
# Ollama: доступна
.\search.ps1 --stats
# Документів: 15234
# Час побудови індексу: 48210 мс
# Потоків індексації: 8
.\search.ps1 --index 8        # довга операція, таймаут 30 хв
# Проіндексовано документів: 15234
# Час: 48210 мс (48.2 с)
$env:SEARCH_URL = "http://192.168.0.10:8080"; .\search.ps1 "white whale"
```

### Коди виходу й помилки

| Код | Коли |
|-----|------|
| 0 | успіх |
| 1 | сервер недоступний, HTTP 400/409/500 (виводиться повідомлення сервера), таймаут, обрив WebSocket |
| 2 | неправильні аргументи: порожній запит, невідомий параметр, дві команди разом |

Помилки йдуть у stderr, результати в stdout. Порожній запит не звертається до сервера й друкує
підказку про використання.

### Кирилиця і кодування (Windows)

CLI надсилає запит і читає відповідь у UTF-8 і завжди друкує UTF-8 незалежно від налаштувань
системи. Консоль Windows за замовчуванням не UTF-8, тому для правильного відображення потрібна
кодова сторінка 65001:

```powershell
chcp 65001
```

Скрипти `search.cmd` і `search.ps1` самі вмикають UTF-8 на час роботи й повертають попередню
кодову сторінку після виходу, тож окремо `chcp` потрібен лише при прямому запуску
`java -jar cli/target/search-cli.jar ...`. Для читабельного шрифту в консолі оберіть Consolas або
Cascadia. Якщо в запиті кирилиця перетворюється на `?` (залежить від системної кодової сторінки
Windows при передачі аргументів у Java), передайте запит через stdin:
`"біла вага" | .\search.ps1 -` (у `cmd` спершу `chcp 65001`, потім `echo біла вага | search.cmd -`).

## Датасет

Джерело: [Text files from Gutenberg database](https://zenodo.org/records/3360392)
(Antonis Michalas, Tampere University, CC BY 4.0). Це англійські книги Project Gutenberg у
форматі `.txt`.

1. Завантажте архів (у цьому проєкті `D1.7GB.zip`) зі сторінки Zenodo.
2. Розпакуйте його в каталог `data/` у корені проєкту:

```bash
mkdir -p data
unzip D1.7GB.zip -d data
```

3. Перевірте кількість файлів і розмір (вимога силабусу: не менше 10 000 документів):

```bash
find data -type f -name '*.txt' | wc -l
du -sh data
```

Каталог `data/` додано в `.gitignore`, датасет у git не потрапляє. Docker монтує його в контейнер
сервера як `/data` (лише читання). Файли можуть лежати у вкладених каталогах: сервер шукає
`*.txt` рекурсивно. Документ це чанк книги (див. розділ "Чанки"), його `doc_id` має вигляд
`шлях відносно data/#N`.

Менші архіви (184 МБ, 357 МБ, 670 МБ, 1 ГБ) зручні для швидкого дебагу та для графіка залежності
часу від розміру даних: розпакуйте потрібний у `data/`.

## Індексація

Після `docker compose up --build` запустіть побудову індексу (одне значення `threads` = кількість
потоків; відповідь приходить, коли індекс готовий, це може тривати хвилини):

```bash
curl -X POST localhost:8080/api/index -H 'Content-Type: application/json' -d '{"threads": 4}'
# {"status":"ok","documents_indexed":10384,"time_ms":123456}

curl localhost:8080/api/stats
# {"documents":10384,"index_build_time_ms":123456,"threads_used":4}
```

(Числа вище лише приклад формату, не результат вимірювання.)

- Повторний виклик будує новий індекс і замінює старий атомарно; поки він будується, `/api/stats`
  показує попередній готовий індекс.
- Якщо індексація вже триває, другий виклик одразу отримує `409`.
- Файл, який не вдалося прочитати, і порожній файл (без жодного терміна) пропускаються з записом
  у лог, решта індексується далі. `documents_indexed` це кількість документів (чанків), а не файлів.
  Після індексації в лозі є рядок `Indexed N books into M documents (chunks)`.
- Кодування: UTF-8, а якщо файл не є коректним UTF-8, то ISO-8859-1.
- Токенізатор: нижній регістр, терміни з літер і цифр довжиною 2..40 символів, англійські
  стоп-слова (`server/src/main/resources/stopwords.txt`), шапка й футер Project Gutenberg
  (між рядками `*** START OF` і `*** END OF`) пропускаються.

## Чанки

У датасеті менше 10 000 книг (2808 книг, 1,59 ГБ), а вимога силабусу ≥ 10 000 документів. Тому
кожна книга ділиться на чанки по ~100 КБ, і **чанк це документ**.

- Розмір задає `CHUNK_SIZE_KB` (за замовчуванням 100). `0` вимикає чанки: файл = документ, `doc_id` без `#`.
- Чанк складається з послідовних рядків тіла книги (без шапки й футера Gutenberg). Він закривається
  на першому рядку, де накопичилось не менше `CHUNK_SIZE_KB * 1024` символів (рядок рахується як
  його довжина + 1 за перенос). Різання лише між рядками, тож слова не розрізаються.
- Останній короткий шматок (менше 1 КБ) приєднується до попереднього чанка, інакше він окремий чанк.
- `doc_id` = `шлях#N`, N від 1, наприклад `gutenberg/moby.txt#3`. Якщо в чанку немає жодного терміна,
  він пропускається, а номери решти чанків не змінюються.
- Сніпет береться лише з рядків свого чанка. Індексатор і сніпети використовують один клас
  `Chunker`, тому межі чанків збігаються.
- Кодування вибирається для всього файлу один раз: UTF-8, а якщо в файлі є хоч один недопустимий
  байт, то ISO-8859-1 (інакше межі чанків могли б розійтися).
- Чанків більше, ніж книг, тому постингів у індексі, ймовірно, більше, ніж без чанків (кожен термін
  записується в кожен чанк, де він є). Точний вплив на пам'ять не виміряно: дивіться рядок
  `Index ready: ...` у лозі після першої реальної індексації.

```powershell
$env:CHUNK_SIZE_KB = "50"; docker compose up --build   # менші чанки, більше документів
$env:CHUNK_SIZE_KB = "0";  docker compose up --build   # без чанків
```

## Пошук

Пошук працює по останньому готовому індексу (спершу виконайте індексацію). Запит розбивається
тим самим токенізатором, що й книги (нижній регістр, без стоп-слів). Режим один: `keyword`
(якщо `mode` пропущено, береться `keyword`).

```bash
curl -s -X POST localhost:8080/api/search -H 'Content-Type: application/json' \
  -d '{"query": "white whale harpoon", "mode": "keyword"}'

curl -s -X POST localhost:8080/api/search -H 'Content-Type: application/json' \
  -d '{"query": "sherlock holmes detective", "mode": "keyword"}'

curl -s -X POST localhost:8080/api/search -H 'Content-Type: application/json' \
  -d '{"query": "pride and prejudice marriage", "mode": "keyword"}'
```

Відповідь (формат):

```json
{"results": [{"doc_id": "<шлях відносно data/>", "score": 1.0, "snippet": "...фрагмент ~200 символів..."}],
 "time_ms": 12}
```

- Повертається до 10 документів, найкращі першими; `score` від 0 до 1 (найкращий = 1.0, 4 знаки);
  рівні оцінки впорядковуються за `doc_id`, тож відповідь завжди однакова.
- Документ підходить, якщо містить хоча б один термін запиту (OR). Чим більше різних термінів
  запиту він містить, тим вище його оцінка.
- Запит лише зі стоп-слів (наприклад `the and of`), невідомі слова або порожній індекс дають
  `200` з порожнім `results`.
- `doc_id` має вигляд `шлях#N` (номер чанка); з `CHUNK_SIZE_KB=0` це просто шлях.
- `snippet` береться з тексту книги (без шапки Project Gutenberg), навколо першого входження
  слова запиту в цьому чанку (не виходить за його межі), обрізані краї позначені `...`; якщо файл не вдалося прочитати, `snippet` порожній.

Формула: `tf = 1 + ln(freq)`, `idf = ln(1 + N/df)`, оцінка документа = сума `вага * tf * idf` по
термінах запиту, помножена на частку знайдених термінів і поділена на `1 + ln(довжина документа)`.

## Ollama і розширення запиту

Розширення запиту (query expansion) просить локальну LLM дати 5-8 ключових слів і синонімів до
запиту. Ці слова додаються до пошуку з вагою 0.5 (слова користувача мають вагу 1.0). Воно
використовується в WebSocket `/ws/search`. `POST /api/search` з `mode: keyword` Ollama не викликає.

**Модель.** Задається змінною `OLLAMA_MODEL` (за замовчуванням `qwen2.5:1.5b`). Для слабкого
комп'ютера підійде мала модель (`qwen2.5:1.5b`, `llama3.2:1b`), для кращої якості більша
(`qwen2.5:3b`). Змінити модель:

```powershell
$env:OLLAMA_MODEL = "llama3.2:1b"; docker compose up --build
```

Сервер сам завантажує модель у фоновому потоці під час старту (до 5 спроб з паузою 10 с) і не
блокує запуск. Прогрес видно в логу: `docker compose logs -f server`. Поки модель не готова, пошук
працює без розширення. Перший запуск може тривати кілька хвилин (завантаження ~1 ГБ).

**Прогрів.** Запит до Ollama містить `"keep_alive": "30m"` (модель лишається в пам'яті 30 хвилин), а після успішної перевірки моделі сервер робить один короткий фоновий запит `Say OK`, щоб модель завантажилась у пам'ять ще до першого пошуку користувача. Помилка прогріву лише потрапляє в лог (`Model warm-up failed`), пошук працює і без неї.

**Перевірка:**

```bash
docker compose exec ollama ollama list          # список завантажених моделей
curl localhost:8080/api/health                  # {"status":"ok","ollama":true}
docker compose logs server | grep -i "model"    # чи модель готова
```

`ollama:true` означає лише те, що сервіс Ollama відповідає, а не те, що модель уже завантажена.

**Збереження моделей.** Моделі лежать в іменованому томі `ollama_models` (`/root/.ollama`), тому
переживають `docker compose down` і перезапуск. Лише `docker compose down -v` видаляє том, і модель
доведеться завантажувати знову.

**Fallback.** Якщо Ollama недоступна, відповідає помилкою, надто повільна (`OLLAMA_TIMEOUT_SECONDS`),
відповіла сміттям або зайнята іншим запитом (одна генерація за раз), розширення просто порожнє, і
пошук іде по оригінальному запиту. Повторні однакові запити беруться з кешу (LRU, 256 записів).

## Пам'ять

Індекс повністю зберігається в пам'яті JVM. У `Dockerfile` задано `-XX:MaxRAMPercentage=75`, тобто
купа може займати до 75% пам'яті контейнера (без обмеження: 75% пам'яті машини). Після кожної
індексації в лозі сервера є рядок `Index ready: ...` з кількістю документів, термінів, постингів і
використаною пам'яттю купи (`docker compose logs server`).

- Під час повторної індексації старий індекс лишається в пам'яті, поки будується новий (щоб пошук
  працював), тому на мить потрібно пам'яті приблизно на два індекси.
- На Docker Desktop (Windows, macOS) перевірте в налаштуваннях, що віртуальній машині виділено
  достатньо пам'яті; значення за замовчуванням може бути замало для великого датасету.
- Обмежити пам'ять сервера можна рядком `mem_limit` у `docker-compose.yml` (закоментований
  приклад там є).
- Якщо з'являється `OutOfMemoryError`, використайте менший архів датасету або збільште пам'ять.

## Тести

```bash
mvn test                 # усі модулі
mvn -pl cli test         # лише CLI
```

Тести CLI не потребують запущеного сервера: REST-режим, `--health`, `--stats` і `--index`
перевіряються проти фейкового сервера на `com.sun.net.httpserver.HttpServer`, WebSocket-режим
проти мінімального WebSocket-сервера на сокетах (`FakeWsServer`).

