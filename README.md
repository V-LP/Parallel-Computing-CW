# Паралельна пошукова система з LLM

Курсова робота з паралельних обчислень.

## Опис

Контейнеризована пошукова система на Java 21. Вона будує інвертований індекс над текстовим
датасетом паралельно (власний thread pool і власна thread-safe структура даних), обробляє
запити від кількох клієнтів одночасно та розширює запит за допомогою локальної LLM (Ollama).

Можливості:

- паралельна побудова інвертованого індексу;
- пошук за ключовими словами;
- розширення запиту (query expansion) через Ollama; якщо Ollama недоступна, пошук іде по
  оригінальному запиту;
- REST API та WebSocket `/ws/search`;
- клієнти: консольний (CLI) і веб-інтерфейс (Web UI);
- запуск однією командою `docker compose up`.

> Статус: каркас проєкту (етап 1). Функціональність додається поетапно, див. `CONTEXT.md`.

## Вимоги

- Docker та Docker Compose (для запуску системи);
- JDK 21 та Maven 3.9+ (лише для локальної розробки без Docker);
- Python 3.10+ з `matplotlib` (лише для бенчмарків у `bench/`);
- місце під розпакований датасет (за описом завдання ~1,7 ГБ для `D1.7GB.zip`);
- пам'ять: індекс зберігається в оперативній пам'яті (див. розділ "Пам'ять").

## Запуск

Запуск усієї системи (сервер + Ollama) однією командою:

```bash
docker compose up --build
```

Сервіси:

| Сервіс | Порт | Призначення |
|--------|------|-------------|
| `server` | 8080 | пошуковий сервер (REST API) |
| `ollama` | 11434 (лише всередині мережі compose) | локальна LLM |

Змінні середовища:

| Змінна | За замовчуванням | Опис |
|--------|------------------|------|
| `PORT` | `8080` | порт сервера |
| `OLLAMA_URL` | `http://ollama:11434` | адреса Ollama |
| `OLLAMA_MODEL` | `qwen2.5:1.5b` | модель для розширення запиту (використовується з етапу 8) |
| `DATA_DIR` | `/data` | каталог з `.txt` файлами датасету (в Docker це `./data`) |

Каталог `./data` монтується в контейнер сервера як `/data` (лише читання).

Перевірка, що сервер працює:

```bash
curl localhost:8080/api/health
# {"status":"ok","ollama":true}
```

Якщо Ollama ще не готова, поле `ollama` буде `false`: сервер при цьому працює.

Збірка fat-jar і запуск без Docker:

```bash
mvn -pl server -am package
PORT=8080 OLLAMA_URL=http://localhost:11434 java -jar server/target/server.jar
```

Локальна збірка:

```bash
mvn compile            # компіляція всіх модулів
mvn test               # тести
mvn spotless:apply     # автоформатування (Google Java Style)
```

## API

| Метод | Шлях | Тіло запиту | Відповідь |
|-------|------|-------------|-----------|
| GET | `/api/health` | - | `{ "status": "ok", "ollama": true }` |
| POST | `/api/index` | `{ "threads": 4 }` | `{ "status": "ok", "documents_indexed": N, "time_ms": T }` |
| POST | `/api/search` | `{ "query": "text", "mode": "keyword" }` | `{ "results": [{"doc_id": "...", "score": 0.95, "snippet": "..."}], "time_ms": T }` |
| GET | `/api/stats` | - | `{ "documents": N, "index_build_time_ms": T, "threads_used": K }` |

Помилки `POST /api/index` і `POST /api/search` (тіло `{ "status": "error", "message": "..." }`):

| Код | Коли |
|-----|------|
| 400 | `/api/index`: некоректний JSON або `threads` поза межами 1..1024 (без тіла або без `threads` береться кількість процесорів). `/api/search`: порожній або відсутній `query`, `mode` не `keyword`, некоректний JSON |
| 409 | інша індексація ще триває |
| 500 | каталог даних (`DATA_DIR`) недоступний |

WebSocket `/ws/search`: клієнт надсилає `{ "query": "..." }`, сервер відповідає по одному
JSON-повідомленню на етап (`query_expansion`, `keyword_search`, `done`).

## Датасет

Джерело: [Text files from Gutenberg database](https://zenodo.org/records/3360392)
(Antonis Michalas, Tampere University, CC BY 4.0). Це англійські книги Project Gutenberg у
форматі `.txt`.

1. Завантажте архів (у цьому проєкті `D1.7GB.zip`) зі сторінки Zenodo.
2. Розпакуйте його в каталог `data/` у корені проєкту:

```bash
mkdir -p data
unzip D1.7GB.zip -d data
```

3. Перевірте кількість файлів і розмір (вимога силабусу: не менше 10 000 документів):

```bash
find data -type f -name '*.txt' | wc -l
du -sh data
```

Каталог `data/` додано в `.gitignore`, датасет у git не потрапляє. Docker монтує його в контейнер
сервера як `/data` (лише читання). Файли можуть лежати у вкладених каталогах: сервер шукає
`*.txt` рекурсивно. Один файл = один документ, його `doc_id` це шлях відносно `data/`.

Менші архіви (184 МБ, 357 МБ, 670 МБ, 1 ГБ) зручні для швидкого дебагу та для графіка залежності
часу від розміру даних: розпакуйте потрібний у `data/`.

## Індексація

Після `docker compose up --build` запустіть побудову індексу (одне значення `threads` = кількість
потоків; відповідь приходить, коли індекс готовий, це може тривати хвилини):

```bash
curl -X POST localhost:8080/api/index -H 'Content-Type: application/json' -d '{"threads": 4}'
# {"status":"ok","documents_indexed":10384,"time_ms":123456}

curl localhost:8080/api/stats
# {"documents":10384,"index_build_time_ms":123456,"threads_used":4}
```

(Числа вище лише приклад формату, не результат вимірювання.)

- Повторний виклик будує новий індекс і замінює старий атомарно; поки він будується, `/api/stats`
  показує попередній готовий індекс.
- Якщо індексація вже триває, другий виклик одразу отримує `409`.
- Файл, який не вдалося прочитати, і порожній файл (без жодного терміна) пропускаються з записом
  у лог, решта індексується далі. Тому `documents_indexed` може бути меншим за кількість файлів.
- Кодування: UTF-8, а якщо файл не є коректним UTF-8, то ISO-8859-1.
- Токенізатор: нижній регістр, терміни з літер і цифр довжиною 2..40 символів, англійські
  стоп-слова (`server/src/main/resources/stopwords.txt`), шапка й футер Project Gutenberg
  (між рядками `*** START OF` і `*** END OF`) пропускаються.

## Пошук

Пошук працює по останньому готовому індексу (спершу виконайте індексацію). Запит розбивається
тим самим токенізатором, що й книги (нижній регістр, без стоп-слів). Режим один: `keyword`
(якщо `mode` пропущено, береться `keyword`).

```bash
curl -s -X POST localhost:8080/api/search -H 'Content-Type: application/json' \
  -d '{"query": "white whale harpoon", "mode": "keyword"}'

curl -s -X POST localhost:8080/api/search -H 'Content-Type: application/json' \
  -d '{"query": "sherlock holmes detective", "mode": "keyword"}'

curl -s -X POST localhost:8080/api/search -H 'Content-Type: application/json' \
  -d '{"query": "pride and prejudice marriage", "mode": "keyword"}'
```

Відповідь (формат):

```json
{"results": [{"doc_id": "<шлях відносно data/>", "score": 1.0, "snippet": "...фрагмент ~200 символів..."}],
 "time_ms": 12}
```

- Повертається до 10 документів, найкращі першими; `score` від 0 до 1 (найкращий = 1.0, 4 знаки);
  рівні оцінки впорядковуються за `doc_id`, тож відповідь завжди однакова.
- Документ підходить, якщо містить хоча б один термін запиту (OR). Чим більше різних термінів
  запиту він містить, тим вище його оцінка.
- Запит лише зі стоп-слів (наприклад `the and of`), невідомі слова або порожній індекс дають
  `200` з порожнім `results`.
- `snippet` береться з тексту книги (без шапки Project Gutenberg), навколо першого входження
  слова запиту; якщо файл не вдалося прочитати, `snippet` порожній.

Формула: `tf = 1 + ln(freq)`, `idf = ln(1 + N/df)`, оцінка документа = сума `вага * tf * idf` по
термінах запиту, помножена на частку знайдених термінів і поділена на `1 + ln(довжина документа)`.

## Пам'ять

Індекс повністю зберігається в пам'яті JVM. У `Dockerfile` задано `-XX:MaxRAMPercentage=75`, тобто
купа може займати до 75% пам'яті контейнера (без обмеження: 75% пам'яті машини). Після кожної
індексації в лозі сервера є рядок `Index ready: ...` з кількістю документів, термінів, постингів і
використаною пам'яттю купи (`docker compose logs server`).

- Під час повторної індексації старий індекс лишається в пам'яті, поки будується новий (щоб пошук
  працював), тому на мить потрібно пам'яті приблизно на два індекси.
- На Docker Desktop (Windows, macOS) перевірте в налаштуваннях, що віртуальній машині виділено
  достатньо пам'яті; значення за замовчуванням може бути замало для великого датасету.
- Обмежити пам'ять сервера можна рядком `mem_limit` у `docker-compose.yml` (закоментований
  приклад там є).
- Якщо з'являється `OutOfMemoryError`, використайте менший архів датасету або збільште пам'ять.

## Структура проєкту

```
.
├── server/                  # сервер (Javalin)
│   └── src/main/java/ua/coursework/engine/
│       ├── api/             # REST і WebSocket маршрути
│       ├── index/           # інвертований індекс, токенізатор, індексатор
│       ├── concurrent/      # власний ThreadPool
│       ├── search/          # SearchService
│       └── llm/             # клієнт Ollama, розширення запиту
├── server/src/main/resources/web/   # Web UI
├── cli/                     # консольний клієнт
├── bench/                   # бенчмарки та графіки (Python)
├── docs/uml/                # UML-діаграми (.puml) і рендер у out/
├── docs/report/             # розділи звіту
├── CONTEXT.md               # контекст проєкту для нових чатів
└── COMMITS.md               # правила commit-повідомлень
```

## UML-діаграми

Джерела в `docs/uml/*.puml`, готові PNG/SVG у `docs/uml/out/`. Перерендерити:

```bash
java -jar plantuml.jar -charset UTF-8 -tpng -o out docs/uml/*.puml
java -jar plantuml.jar -charset UTF-8 -tsvg -o out docs/uml/*.puml
```
