# Бенчмарки і тестові запити (етапи 12 і 13)

Скрипти замірюють пошукову систему, що працює в Docker, і будують графіки (етап 12), а
`run_queries.py` проганяє таблицю тестових запитів (етап 13, розділ нижче). Усі цифри беруться
лише з вимірювань: кожен замір одразу дописується в CSV у `bench/results/`, а графіки й таблиці
будуються тільки з цих CSV. Якщо CSV порожній, `plot.py` зупиняється з повідомленням;
`summarize.py` пропускає розділ без даних і зупиняється, лише коли даних немає зовсім.

| Файл | Призначення |
|------|-------------|
| `run_bench.py` | запускає експерименти (`threads`, `size`, `search`, `ws`, `env`, `all`) |
| `plot.py` | графіки (PNG) з CSV |
| `summarize.py` | `results/summary.md` (таблиці медіан, прискорення, ефективності) |
| `benchlib.py` | чисті функції: перцентилі, розбір рядка `Index ready`, підсумки, CSV |
| `dockerutil.py` | `docker compose`, HTTP, збір середовища |
| `queries.txt` | 30 англійських запитів (1-3 слова, часті й рідкісні слова, імена) |
| `docker-compose.bench.yml` | override: монтує `${BENCH_DATA_DIR}` як `/data:ro` |
| `test_benchlib.py` | юніт-тести без сервера |
| `run_queries.py` | таблиця тестових запитів: REST і WebSocket, звіт у `docs/report/` (етап 13) |
| `test_queries.json` | 26 тестових запитів (`id`, `category`, `query`, `purpose`) |
| `test_run_queries.py` | юніт-тести `run_queries.py` без сервера |
| `requirements.txt` | `matplotlib`, `websockets` |

Код сервера скриптами етапу 12 не змінюється. (На етапі 13 сервер отримав лише `temperature: 0` і
`OLLAMA_SEED` для відтворюваного розширення.)

## Вимоги

- Windows + Docker Desktop (Compose v2), контейнер сервера в `docker compose`, API на `localhost:8080`.
- **Docker Desktop: мінімум 8 ГБ пам'яті** (Settings -> Resources; для бекенду WSL2 це `memory=` у
  `%UserProfile%\.wslconfig`, потім `wsl --shutdown`). JVM бере 75% пам'яті контейнера під купу.
  Для найбільшого набору (D1.7GB) пам'яті може знадобитися більше: якщо контейнер перезапускається
  з кодом 137, це нестача пам'яті.
- Python 3.10+, `pip install -r bench/requirements.txt` (`matplotlib` для графіків, `websockets` для
  `run_queries.py` і необов'язкового експерименту `ws`).
- Датасет: `./data` (D1.7GB) і підмножини `./data_extra/D184MB`, `D357MB`, `D670MB`, `D1GB`
  (інші каталоги можна задати параметром `--datasets`).
- Образ зібраний: `docker compose build server`. Для `ws` модель Ollama вже завантажена
  (`docker compose up -d`, дочекатися завантаження моделі).

## Перед запуском

Результат залежить від того, що ще навантажує комп'ютер.

- Закрийте браузер, IDE, месенджери, Docker-контейнери, що не потрібні, і важкі програми.
- Антивірус (Windows Defender) сканує кожен прочитаний файл і сильно сповільнює читання датасету.
  На час замірів додайте в винятки каталог проєкту або вимкніть сканування в реальному часі, а потім
  поверніть налаштування.
- Ноутбук підключіть до живлення, схема живлення «Висока продуктивність». Не користуйтеся
  комп'ютером під час замірів.
- Не запускайте інший `docker compose up` на порту 8080.

**Попередження про bind-mount у Windows.** Каталог `./data` монтується в контейнер зі
сховища Windows (`C:\...`), а це значно повільніше за файлову систему Linux. Індексація читає
тисячі файлів, тож абсолютні часи й частка послідовного читання залежать від цього. Швидше, якщо
проєкт і датасет лежать усередині WSL2 (`\\wsl$\...` або `~/` у дистрибутиві) і команди
запускаються звідти. У звіті вкажіть, як саме змонтовано дані. Порівнювати між собою можна лише
виміри, зроблені в одній конфігурації.

## Запуск

Усі команди з кореня репозиторію (PowerShell). Спочатку подивіться план, нічого не запускаючи:

```powershell
python bench\run_bench.py all --dry-run
```

Параметри, спільні для експериментів: `-R/--repeats` (повторів, за замовчуванням 3), `--seed` (порядок
прогонів, 42), `--url` (http://localhost:8080), `--settle` (скільки секунд чекати, поки сервер
закінчить фонове завантаження й прогрів моделі, 30; `0` вимикає), `--keep-old` (дописувати у наявні
CSV; інакше старий CSV відкладається в `*.csv.tmp`, який git ігнорує).

### 1. Індексація від кількості потоків

```powershell
python bench\run_bench.py threads                       # threads = 1,2,4,8,16, R = 3
python bench\run_bench.py threads --threads 1,2,3,4,6,8,12,16 -R 5
```

Перед КОЖНИМ прогоном: `docker compose restart server`, очікування `GET /api/health`, очікування
прогріву моделі, `POST /api/index {"threads": p}`. Із логу контейнера береться рядок
`Index ready:` (документи, терміни, постинги, купа). Порядок значень `threads` перемішується в
кожному повторі. Перший прогін усього експерименту позначається `cold=1` (холодний файловий
кеш): у статистику (медіана, мін, макс) він не входить, на графіку показаний хрестиком.

**Перевірка корректності:** кількість документів, термінів і постингів має збігатися в усіх
прогонах. Якщо ні, скрипт зупиняється з кодом 3 (ознака гонки в індексі); рядок із розбіжністю вже
записаний у CSV.

Результат: `results/index_threads.csv`.

### 2. Індексація від розміру даних

```powershell
python bench\run_bench.py size                          # 5 наборів, 8 потоків
python bench\run_bench.py size --size-threads 4 -R 3
python bench\run_bench.py size --datasets "A=data_extra\D184MB,B=data"
```

Для кожного набору контейнер створюється заново з `-f docker-compose.yml -f
bench\docker-compose.bench.yml` і `BENCH_DATA_DIR=<каталог>` (одна команда `docker compose restart`
новий каталог не змонтує); для повторного прогону того ж набору достатньо `restart`. Порядок наборів
перемішується між повторами. Результат: `results/index_size.csv` (кількість файлів `.txt` і розмір
рахуються за каталогом).

### 3. Пошук від кількості клієнтів

```powershell
python bench\run_bench.py search                        # M = 1,2,4,8,16,32, K = 50, R = 3
python bench\run_bench.py search --clients 1,4,16 --requests 100 --index-threads 8
```

Спочатку перезапуск сервера й свіжа індексація, потім один прогрівальний прохід по всіх запитах
(не записується). Кожен із M клієнтів (потік Python з постійним з'єднанням) у замкненому циклі
надсилає K запитів `POST /api/search` з `mode: keyword`, наступний запит після відповіді на
попередній. Записуються затримка кожного запиту і час усього раунду. Результат:
`results/search_requests.csv`, `results/search_runs.csv`.

### 4. WebSocket-пайплайн (необов'язково)

```powershell
pip install -r bench/requirements.txt
python bench\run_bench.py ws                            # M = 1,2,4 одночасних клієнтів
```

Потрібна працююча Ollama з моделлю. Запити в кожному раунді різні й не повторюються протягом
експерименту (кеш `QueryExpander` інакше дав би миттєву відповідь). Для кожного клієнта
записуються час до етапу `query_expansion` (від відправки), `time_ms` етапу `keyword_search` (з
сервера) і кількість розширених термінів. Нуль термінів означає, що семафор не пустив запит до
Ollama вчасно й спрацював fallback. Без `websockets` експеримент пропускається.
Результат: `results/ws_stages.csv`.

### 5. Середовище, графіки, підсумок

```powershell
python bench\run_bench.py env          # лише environment.json (експерименти пишуть його й самі)
python bench\plot.py                   # усі графіки, для яких є CSV
python bench\plot.py threads           # або один експеримент: threads | size | search | ws
python bench\summarize.py              # results\summary.md
```

Графіки (PNG у `results/`): `index_time.png` (медіана, смуга мін-макс, ідеальна лінія 1/p,
холодний прогін окремо), `index_speedup.png` S(p), `index_efficiency.png` E(p) = S(p)/p,
`index_size.png` (час від розміру в МБ і від кількості документів), `search_throughput.png`,
`search_latency.png` (p50, p95, p99), `ws_stages.png`.
`environment.json`: ядра й ОЗУ хоста, ОС, `docker info` (ядра й пам'ять Docker), `CHUNK_SIZE_KB`,
кількість файлів і розмір кожного датасету, git-хеш, дата.

Усе одразу: `python bench\run_bench.py all`.

## Юніт-тести

```powershell
python -m unittest discover -s bench -p "test_*.py" -v
```

Перевіряють перцентили, розбір рядка `Index ready`, підсумки (медіани, прискорення, ефективність,
холодні прогони), перевірку однаковості лічильників, план прогонів, CSV і `summary.md`. Сервер і
Docker не потрібні.

## Як читати результати і що враховувати

- S(p) = T(1)/T(p), E(p) = S(p)/p, T = медіана `time_ms` з відповіді `POST /api/index`.
  Для S і E потрібні прогони з `threads=1`.
- Купа (`heap_mb`) береться з логу сервера «наближено, може містити сміття», це не точний обсяг
  індексу.
- Перцентилі: найближчий ранг по всіх запитах усіх повторів для даного M. Пропускна здатність:
  успішні запити, поділені на час раунду. Запити не з кодом 200 записуються зі `status`, у
  перцентили не входять; на екран виводиться попередження.
- Клієнт (Python) працює на тому ж комп'ютері, що й Docker, тож при великих M він ділить із
  сервером процесор, а GIL обмежує сам клієнт. Це входить у вимірювану систему; про це
  треба сказати у звіті.
- Набір запитів у `queries.txt` складено вручну, частка порожніх відповідей показана в `summary.md`.
- Ядра Docker (`NCPU` з `docker info`) можуть бути меншими за ядра хоста: на графіках позначена
  вертикальна лінія з кількістю ядер Docker.

## Якщо щось пішло не так

- `Сервер не став готовим`: `docker compose logs server`, перевірте порт 8080.
- Контейнер перезапускається, код 137: збільште пам'ять Docker Desktop.
- `HTTP 409`: індексація вже йде, зачекайте або виконайте `docker compose restart server`.
- `docker` не знайдено: запустіть Docker Desktop.
- Перервали прогін (Ctrl+C): уже зроблені виміри лишаються в CSV; щоб почати заново, просто
  запустіть експеримент ще раз (старий CSV буде відкладено).

## Таблиця тестових запитів (етап 13)

Описано в кореневому `README.md`, розділ «Тестові запити». Коротко (з кореня репозиторію):

```powershell
python bench\run_queries.py                  # docs\report\test-queries.csv і .md
python bench\run_queries.py --no-ollama      # перевірка fallback (Ollama вимкнена вручну)
```

Кожен запит виконується двічі (холодний і теплий прогін), у кожному прогоні REST (без розширення) і
WebSocket (з розширенням). Колонки «Релевантність» і «Коментар» студент заповнює вручну; наявні
`.md` і `.csv` без `--force` не перезаписуються.

## Порядок запусків і стан контейнера

Експерименти етапу 12 перезапускають і перестворюють контейнер `server`, тому:

- Після `size` контейнер може лишитися змонтованим на меншому наборі (порядок наборів перемішується,
  а `restart` mount не змінює). Перед `search`, `run_queries.py` і звичайною роботою поверніть
  основний набір: `docker compose up -d --force-recreate server` (без `bench/docker-compose.bench.yml`).
  Експеримент `search` сам створює контейнер на `--data-dir` (за замовчуванням `./data`).
- Індекс і кеш розширень живуть у пам'яті й зникають після перезапуску сервера: перед
  `run_queries.py` знову виконайте `.\search.ps1 --index`.
- Бенчмарки етапу 12 і таблицю запитів запускайте окремо один від одного, не одночасно.
- Для перевірки fallback (`--no-ollama`) потрібен свіжий процес сервера (`docker compose restart server`
  і повторна індексація), бо кеш розширень віддає їх і при вимкненій Ollama.
